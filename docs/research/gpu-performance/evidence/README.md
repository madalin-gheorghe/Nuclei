## Timing interpretation

`GpuMsPerStep` is elapsed GPU timeline time for the whole batch divided by steps. It can include queue idle time. `PassMsPerStep` contains elapsed named intervals inside `Step`; these are not hardware utilization counters. `WallMsPerStep` includes the batch-end synchronization and query resolution. `SubmitMsPerStep` includes blocking calls performed during advance, including raw field readbacks when enabled.

The batch-end `SynchronizeActiveParticleCount` call supplies a completion fence. A separate warm-up step exercises timestamp-query storage after the requested simulation warm-up. Batches then continue the evolving simulation rather than resetting it. Dynamic tests prevent mutations and check that the active particle count remains unchanged.

The research harness calls raw CPU field readback and `CreateVoxelFieldPreviewFrame` after `Step`. Therefore copies, CPU array work, gradient generation and intervening GPU queue gaps are not all included in named intervals. The aggregate script reports the difference between total GPU timeline and named intervals as **unattributed time**, not pure copy or gradient execution time.

Independent processes and GPU profiles were run sequentially. Different configurations were not randomized or counterbalanced. These are bottleneck profiles, not acceptance-quality speedup comparisons. The ten baseline batches in `intro250.json` come from two fresh engines; other scenarios have five batches from one engine. Ranges are ranges of batch averages. Population correctness checks passed; field equivalence, network morphology, viewport rasterization, meshing and Grasshopper output conversion were not tested.

## Fixture

All profiles use cubic 3D fields and one species/group at a time. Voxel size is 1. Dispersed initial positions have unique interior parent voxels; headings and scalar fields are generated by the deterministic hash in the harness. This is synthetic input, not a Grasshopper document replay. Initial scalar values are 0.100–0.355; ants use that distribution in both pheromone fields and zero scalar slime density. Half the ants initially carry food and their launch-boundary flags are set.

`--intro-profile` sets speed 3, sensor distance 9, sensor angle 45 degrees, rotation 45 degrees, slime deposit 1 and ant deposit 10. Slime settings are range 1, diffusion 0.15, gradual weighting 0.5, decay 0.01, wrapped boundaries. Ant settings are range 2, food/base diffusion 0.1, decays 0.0001/0.0005, closed boundaries and base wander 0.15. Other settings use the loaded backend's defaults. `slime60` is a fixture label: it means 90,000 particles by default here; the million-particle run overrides it.

`--sources 4096` inserts evenly spaced source voxels, with value 100 for ant food or 0.04 for slime food. It is a source-presence test, not a realistic food-placement model. Some ant source indices may fall on closed boundaries.

`--dynamic-scan` enables death checks every step, minimum age 0, death/division neighbour radii 3, permitted neighbour count 0 through `int.MaxValue`, minimum population 0 and maximum equal to initial capacity. Division remains disabled. The current code publishes both neighbour-count observables, but no actual birth or death is expected. The whole marked dynamic interval includes more than just its three axis-sum kernels.

`--cpu-fields` reads scalar density and, for ants, both pheromone fields plus remaining food when available. It intentionally stops before frontend output conversion. `--preview single` requests field 10 (combined ant pheromones) for ants and field 7 (slime chemoattractant) for slime, including a gradient frame. It publishes but does not render that frame. `--trails` enables shared trail publication with history length 32 and frequency 1; no external consumer draws or contends for the trail texture.

The backend normalizes requested preview scales below 10 to 1. Accordingly, `preview-trails250-scale2.json` is a repeated full-resolution configuration, **not a successful resolution reduction**. Its slightly different timings must not be reported as a scale-2 optimization.

## Reproduction

Run from `C:/Nuclei`. The existing backend/GHA and dependencies must already be available in the build directory. Rebuilding the harness does not rebuild production. These commands reproduce the configurations; different drivers, binaries or background load can change timings. Run commands one at a time, without concurrent compilation or GPU benchmarks.

```powershell
dotnet build tools/Nuclei.GpuResearchProbe/Nuclei.GpuResearchProbe.csproj -c Release -v quiet
```

The original baseline used the existing ant performance harness:

```powershell
dotnet tools/Nuclei.AntPerformanceProbe/bin/Release/net8.0-windows/Nuclei.AntPerformanceProbe.dll --intro-profile --species ants,slime,slime60 --preview off --particle-preview --variants current,current --warmup 200 --steps 20 --repeats 5 --json docs/research/gpu-performance/evidence/intro250.json
```

Additional profiles used the research harness:

```powershell
dotnet tools/Nuclei.GpuResearchProbe/bin/Release/net8.0-windows/Nuclei.GpuResearchProbe.dll --intro-profile --species ants,slime60 --preview off --dynamic-scan --warmup 200 --steps 20 --repeats 5 --json docs/research/gpu-performance/evidence/dynamic250.json

dotnet tools/Nuclei.GpuResearchProbe/bin/Release/net8.0-windows/Nuclei.GpuResearchProbe.dll --intro-profile --species ants,slime60 --slime-particles 1000000 --preview off --warmup 600 --steps 20 --repeats 5 --json docs/research/gpu-performance/evidence/static250-million.json

dotnet tools/Nuclei.GpuResearchProbe/bin/Release/net8.0-windows/Nuclei.GpuResearchProbe.dll --intro-profile --species ants,slime60 --preview off --sources 4096 --cpu-fields --warmup 50 --steps 10 --repeats 5 --json docs/research/gpu-performance/evidence/readback-food250.json

dotnet tools/Nuclei.GpuResearchProbe/bin/Release/net8.0-windows/Nuclei.GpuResearchProbe.dll --intro-profile --species ants,slime60 --preview off --sources 4096 --warmup 50 --steps 10 --repeats 5 --json docs/research/gpu-performance/evidence/food250.json

dotnet tools/Nuclei.GpuResearchProbe/bin/Release/net8.0-windows/Nuclei.GpuResearchProbe.dll --intro-profile --species ants,slime60 --preview single --particle-preview --trails --warmup 100 --steps 10 --repeats 5 --json docs/research/gpu-performance/evidence/preview-trails250.json
```

Recompute aggregate means, stage shares and residuals with Python:

```powershell
python docs/research/gpu-performance/summarize.py
```

The production backend writes diagnostic preview logs under `C:/Nuclei/Nuclei-v4/BenchmarkSuite1` during publication. Its synchronous log writes were left enabled and may contribute to CPU submission cost. They are part of the measured current behaviour, not instrumentation added to a production shader for these experiments.
